# 控制与校时修复（2026-09-20）

现场证据：A 解锁成功后约 0.5 秒触发 MOTION_FAULT；三次 SSH 估计 A 比地面站慢约 0.95 秒，B 慢约 33108 秒，两个机器人 timedatectl 均报告未同步。机器人只接受 ARM/STOP 之后、年龄在 `[0, 0.5)` 秒内的命令，因此解锁服务成功不代表运动命令被接受。

此次保留命令时效、原生 500ms 看门狗、STOP 和未标定 Z 轴限制。地面站显示心跳时间差（包含传输延迟，不等于精确时钟偏差），离线或时间差超出 −0.1～+0.25 秒时拒绝发起 ARM/自动运行，并给出提示；STOP 不受此检查限制。机器人对被拒绝的时间戳记录限频诊断，不再静默丢弃。

夹持轴按用户确认支持 −1000～+1000。A/B 控制配置、Python EtherCAT 适配器、原生驱动三层同步修正；界面正负按钮保留，单次测试力矩仍为配置中的 50。B 的 CANopen、RGB 相机和雷达配置未改动。

## 首次启用

先退出地面站和两个机器人测试程序，再在各自终端执行下面命令。脚本检测到本机测试进程尚在运行会拒绝执行，避免运行中跳变系统时间。

地面站 `/home/sgcc/robot_test_system`：

```bash
sudo ./scripts/setup_site_time_sync.sh ground
```

地面站首次需要通过 apt 安装 chrony，需可用软件源；脚本备份原配置，保留上游时间源，增加局域网授时。地面站地址保持 `192.168.10.4`，局域网允许 UDP 123。离线授时使用 chrony local reference，参见 [chrony 官方配置说明](https://chrony-project.org/doc/4.2/chrony.conf.html)。

Robot A `/home/phi/robot_test_system`：

```bash
sudo ./scripts/finish_control_fix.sh a
```

Robot B `/home/phi/robot_test_system_git`：

```bash
sudo ./scripts/finish_control_fix.sh b
```

机器人脚本配置现有 systemd-timesyncd 向地面站同步，备份并原子替换配置所指向的 EtherCAT 程序，恢复 `cap_net_raw`。B 的实际 EtherCAT 程序仍在 `/home/phi/robot_test_system/.local-deps/bin/eyou_agent`，CANopen 程序不替换。

两台机器人检查：

```bash
timedatectl status
timedatectl timesync-status
```

确认 `System clock synchronized: yes`，时间源为 `192.168.10.4`。校时配置持久保存，重启后自动运行；先开地面站，机器人网络就绪并同步后再启动控制。地面站心跳时间差应接近 0。若未同步，检查授时服务、地址和 UDP 123 连通性。

## 日常启动

地面站无需 sudo，在登录桌面的普通用户终端执行：

```bash
./scripts/start_ground_dual.sh
```

Robot A：`sudo ./scripts/start_robot_a_control.sh`

Robot B（注意使用 `_git` 工程目录）：`sudo ./scripts/start_robot_b_control.sh`

以上仍是启动后未使能状态，按住按钮才请求解锁和运动。Qt Session DBus 提示属于桌面会话环境提示，本次已确认的命令拒绝原因是时钟差及旧负力矩限制。
